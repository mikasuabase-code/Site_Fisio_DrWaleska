## 1. Relacionamento entre as tabelas

```
admins            isolada (login do painel)
settings          isolada (PK textual chave)
exercises         isolada (biblioteca, sem vinculo paciente)

services
    ^

    ^        ^        ^        ^        ^        ^

    |                 sem colunas extraidas nesta etapa)
```

Regras:

- Todo `patient_id` aponta para `registrations.id`.
- `waitlist.registration_id` aponta para `registrations.id`.
- `appointments.service_id` e `payments.service_id` apontam para `services.id`.
- `appointments.dupla_id` aponta para `duplas.id` (nullable).
- `evolutions.appointment_id` e `payments.appointment_id` apontam para `appointments.id` (nullable).
- `duplas.paciente1` / `paciente2` continuam jsonb (o Flask le/grava snapshot). Nesta primeira migracao **nao** existem `paciente1_id` / `paciente2_id`.
- Nomes denormalizados (`patient_name`, `servico`, `service_name`) permanecem para o painel continuar funcionando sem JOIN obrigatorio.

`payments.patient_id` vs `registration_id` (hoje duplicados):

- Nos 5 registros atuais, os dois campos sao sempre o mesmo `registrations.id`.
- Nesta primeira migracao as duas colunas permanecem **reais** e ambas FK para `registrations.id`.
- Sem coluna gerada, sem trigger. A carga copia o mesmo ID para `patient_id` e `registration_id`.
- Segunda etapa (depois de testes): simplificar para uma unica coluna.

## 3. Mapeamento SQLite -> PostgreSQL

| Tabela SQLite | Tabela PG | PK | Conversao principal | FK proposta |
|---|---|---|---|---|
| admins | admins | INTEGER identity | `criadoEm` TEXT -> timestamptz; hash scrypt intacto | nenhuma |
| services | services | INTEGER identity | `lista_espera`/`ativo` 0/1 -> boolean; `valor` REAL -> numeric(10,2) | nenhuma |
| registrations | registrations | INTEGER identity | `nascimento` TEXT -> date; `dias`/`motivos` TEXT JSON -> jsonb | `servico_id` -> services(id) ON DELETE SET NULL |
| waitlist | waitlist | INTEGER identity | `nascimento` TEXT -> date | `registration_id` -> registrations(id) ON DELETE SET NULL |
| duplas | duplas | INTEGER identity | `paciente1`/`paciente2` TEXT JSON -> jsonb; `criadaEm` TEXT naive -> timestamptz `America/Sao_Paulo` | nenhuma FK extraida nesta etapa |
| appointments | appointments | INTEGER identity | `starts_at`/`ends_at` TEXT naive -> timestamp (sem tz) | `patient_id` -> registrations; `service_id` -> services; `dupla_id` -> duplas. Todos SET NULL |
| payments | payments | INTEGER identity | `amount` REAL -> numeric(10,2); `paid_at` TEXT -> timestamptz `America/Sao_Paulo` | `patient_id` e `registration_id` ambas reais, ambas FK -> registrations(id); `appointment_id` -> appointments; `service_id` -> services |
| evaluations | evaluations | INTEGER identity | `evaluated_at` TEXT -> date | `patient_id` -> registrations |
| evolutions | evolutions | INTEGER identity | `evolution_date` TEXT -> date | `patient_id` -> registrations; `appointment_id` -> appointments |
| exercises | exercises | INTEGER identity | so tipos | nenhuma |
| documents | documents | INTEGER identity | so tipos | `patient_id` -> registrations |
| settings | settings | TEXT (`chave`) | `valor` TEXT JSON -> jsonb (arrays e strings JSON ja existentes) | nenhuma |
| sqlite_sequence | **nao criar** | — | usar `setval` nas sequences do PG apos a carga | — |

Nomes de coluna camelCase (`criadoEm`, `atualizadoEm`, `criadaEm`) ficam entre aspas no PG para o Flask nao precisar renomear agora.

Carga com ID explicito (`GENERATED BY DEFAULT` permite INSERT com `id`):

## 6. Pontos a adaptar no Flask depois da migracao

Nao alterar agora. Lista para quando o adapter Postgres existir:

1. Trocar `sqlite3` por psycopg (ou postgrest via service_role). `DB_BACKEND=supabase` hoje nao faz nada.
2. Placeholders `?` -> `%s`. `row_factory` / `dict(row)` equivalentes.
3. `PRAGMA foreign_keys` some; FKs passam a ser reais (INSERT com `patient_id` invalido vai falhar).
4. Booleanos: parar de gravar `0/1`; ler `True/False` em vez de `bool(r["lista_espera"])` sobre inteiro.
5. JSON: psycopg devolve `list`/`dict` em jsonb. `json.loads(d["dias"])` quebra se ja vier lista. Normalizar no adapter.
6. Datas: `date`/`datetime` em vez de string. `calc_idade` e a agenda esperam `"YYYY-MM-DD"` / `"YYYY-MM-DD HH:MM:SS"`. Serializar no adapter para o JSON da API nao mudar.
7. Colunas camelCase exigem aspas no SQL PG (`"criadoEm"`). O adapter pode citar identificadores.
8. `payments.patient_id` e `payments.registration_id` continuam as duas colunas reais. O INSERT atual do Flask ja envia as duas; nenhuma mudanca de SQL nesse ponto nesta etapa.
9. `lastrowid` -> `RETURNING id`.
10. `ON CONFLICT(chave)` do settings ja e valido no PG.
11. Auth permanece Flask + cookie + hashes scrypt. Nao migrar para Supabase Auth nesta etapa.
12. Site publico (`GET /api/services`, `POST` cadastro, `GET /api/clinica`) continua no Flask. Nao expor tabela `services` ao `anon` so porque o site e publico.
13. A chave `service_role` fica so no `.env` do servidor. Nunca no frontend, no GitHub, no HTML/JS ou em arquivos publicos.

## 7. Estrategia de RLS / autorizacao

Objetivo: dados clinicos e financeiros inacessiveis pela chave publica.

| Papel | Chave | Acesso |
|---|---|---|
| `anon` | anon / publishable | nenhum (RLS on + FORCE + REVOKE + zero policy) |
| `authenticated` | JWT GoTrue | nenhum (auth nao e GoTrue) |
| `service_role` | so no servidor Flask, `.env`, nunca no frontend | total, ignora RLS |

Detalhes:

- RLS + `FORCE ROW LEVEL SECURITY` em **todas** as 12 tabelas, inclusive `services` e `settings`. O catalogo publico sai pelo Flask, nao pelo PostgREST.
- Nenhuma `CREATE POLICY`. Sem policy, `anon`/`authenticated` nao leem nem escrevem.
- `REVOKE ALL` em tabelas, sequences e funcoes para `anon` e `authenticated`.
- Tabelas mais sensiveis: `admins`, `registrations`, `payments`, `evaluations`, `evolutions`, `documents`, `appointments`, `duplas`, `waitlist`.
- Login continua `POST /api/admin/login` -> `session["admin_id"]` -> `@login_required`. O cliente JS nunca recebe a service_role.
- Se a service_role vazar: rotacionar no painel Supabase. `.env` permanece no `.gitignore`.
- Nao usar o schema antigo (`staff_users` / UUID / policies hipoteticas de `patients`).

## Decisoes resolvidas (fechadas nesta revisao)

1. **payments.registration_id e patient_id:** ambas colunas reais, ambas FK para `registrations.id`. Sem GENERATED, sem trigger. Carga copia o mesmo ID nas duas. Simplificar so numa segunda etapa, depois dos testes.
2. **duplas.criadaEm (e demais auditorias):** timestamptz. Valores naive do SQLite interpretados como `America/Sao_Paulo`. `starts_at`/`ends_at` da agenda permanecem timestamp sem tz.
3. **duplas.paciente1 / paciente2:** jsonb puro nesta primeira migracao. Sem `paciente1_id` / `paciente2_id`.
